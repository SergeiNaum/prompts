Реализовать в существующем Python 3 приложении следующий процесс. Детали реализации агент выбирает самостоятельно, сохраняя описанное поведение.
1. Цель. table_1 в PostgreSQL/PostGIS 3.3.3 остаётся входной таблицей внешнего ежедневного ETL. table_2 хранит данные для приложения и контур здания из 2ГИС. Допустима задержка обогащения.
2. Проверить исходные условия. В table_1 есть id bigint IDENTITY PRIMARY KEY. Пока предполагается, что объект сохраняет id между загрузками; проверить это по ETL. Если предположение неверно, выбрать устойчивый ключ. Определить данные для поиска здания и надёжный признак завершения ETL. Уточнить, содержит ли источник актуальный полный снимок.
3. Подготовить модель данных. В table_2 хранить ключ источника, необходимые исходные поля, ID здания 2ГИС, геометрию PostGIS, статус обогащения, версию данных поиска и метаданные повторных попыток. WKT преобразовывать в геометрию с проверкой типа, валидности и системы координат.
4. Реализовать пакетную синхронизацию. После успешного ETL читать согласованный снимок table_1 и выполнять SQL UPSERT внутри БД. Новые записи ставить на обогащение. При изменении обычных полей сохранять контур. При изменении данных поиска сбрасывать неподходящий результат, увеличивать версию поиска и назначать повторную обработку. Исчезнувшие записи деактивировать только при подтверждённом полном снимке. Обновления и отметку обработанной загрузки фиксировать атомарно; исключить параллельные синхронизации.
5. Реализовать фоновое обогащение. Получать контуры для ожидающих обработки записей. HTTP выполнять вне транзакций БД. Сохранять ответ только для активной записи с той же версией данных поиска. Различать успешный результат, отсутствие совпадения, неоднозначность и техническую ошибку. Предусмотреть тайм-ауты, ограничения запросов, повторы с увеличением интервала и восстановление после перезапуска.
6. Организовать запуск. Использовать две независимые задачи: синхронизация завершённых загрузок и регулярная обработка обогащения. SQLAlchemy и APScheduler — базовый вариант; учитывать существующий стек. Состояние обработки хранить в PostgreSQL. Приложение должно поддерживать записи, контур которых ещё не получен.
7. Проверить результат. Повторная синхронизация сохраняет готовые контуры; изменение обычных полей не вызывает повторный поиск; изменение адреса запускает обработку; устаревший ответ API отклоняется; сбой 2ГИС допускает восстановление; незавершённый ETL не вызывает массовую деактивацию.
Результат работы агента: миграции, реализация обеих задач, проверки ключевых сценариев и короткая инструкция запуска. Неизвестные детали выяснять из проекта; существенные допущения явно фиксировать.
